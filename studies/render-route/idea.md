# 呈现路由

同一轮回答如果只会倒进一个文本框，读者分不清这是一段话、目录里的一个组件，还是一份必须跟宿主隔开的文档。名字不在目录里、props 对不上 schema、JSON 还没写完，也会被直接挂上页面。

## 规则

每一轮只到达一个路由对象。宿主在三种表面里提交一种：

1. **纯文本**。说明、事实、写作。不升格成组件。
2. **原生组件**。组件名必须出现在 `lightui.genui` 当前契约里，props 必须通过该组件的 schema。v0 只有 `Text`，`content` 是字符串，不允许额外字段。
3. **iframe 沙盒**。契约表达不了的版式或交互，放进不带宿主同源权限的文档。这一则只呈现这份文档。

依据是模型声明的 `surface`，加上宿主校验。三种表面都合法时，宿主尊重声明，并把依据原文留在画面上。宿主不另猜「哪种更好看」。

降级只有三条，都发生在挂载之前：

- 组件名不在契约里：不挂这个名字，改交文本回退。
- props 校验失败：不挂，改交文本回退，并列出 schema 错误。
- 流式半截：JSON 没闭合之前不提交任何表面。半截字符串里出现 `native` 或 `Text`，也不提前挂组件。

## 为什么朴素做法更差

一律文本，可改人数的估算器和一句话长得一样，人没法操作。一律按名字渲染，未知组件和坏 props 会炸开或留白。流式途中先挂组件，半包会被当成一种表面，下一包再拆掉。宿主擅自改写一个本来合法的选择，依据和画面就对不上，这一轮为什么走这条表面也说不清。
